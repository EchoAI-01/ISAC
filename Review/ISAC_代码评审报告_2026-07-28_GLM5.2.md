### 1.2 适配器实现

**`FeishuAdapter` — AES-256-CBC 解密** ✅
解密流程 `key=SHA256(encrypt_key)` → `enc=base64decode(encrypt)` → `iv=enc[:16]` / `ciphertext=enc[16:]` → `AES-CBC decrypt` → `PKCS7(128).unpad` → `json.loads`，与飞书官方文档"接收事件"小节字节序一致。`len(enc) < 16 + 16` 的密文长度守卫是合理的防御性判定。

**`FeishuAdapter` — tenant_access_token 缓存** ✅
`expires_at = time.monotonic() + max(60, expire - 60)`，提前 60s 刷新 + `max(60, ...)` 兜底异常短的 expire 值。用 `time.monotonic()` 而非 `time.time()` 规避了系统时钟回拨的风险。

**`FeishuAdapter.send()` — code 判定** ✅
```python
code_raw = resp.get("code")
code = -1 if code_raw is None else int(code_raw)
```
显式 `is None` 判定，避免了 `0 or -1 == -1` 的 falsy 陷阱（飞书 `code=0` 才是成功）。`_get_tenant_access_token` 同样采用此模式。两处 `# NOTE:` 注释解释了为何不能用 `or`，是这类 falsy 边界用例应有的告警。

**`QQOfficialAdapter.send()` — code 判定不一致** ⚠️ Required

```python
# isac/channel/adapters/qq_official/adapter.py:337
code = int(resp.get("code", 0) or 0)
```

三处问题：

1. **`None or 0 == 0`：** 若 QQ API 响应体里 `code` 字段显式为 `None`（理论上少见，但 QQ 网关异常返回或代理层透传时可能出现），会被当作 `0` 误判为成功。
2. **缺失默认 0：** `resp.get("code", 0)` 在字段缺失时返回 `0`，与 `FeishuAdapter` 的 fail-closed（缺失 → -1）策略相反，按"缺失即成功"处理。
3. **与同文件内 `_handle_callback` 的 op 判定不一致：** 第 156-157 行 `op_raw = payload.get("op", -1); op = -1 if op_raw is None else int(op_raw)`，与 `send()` 第 337 行写法不统一，给读者带来"为什么 op 要 is None 而 code 不要"的认知负担。

**建议修复：** 统一为 `code_raw = resp.get("code"); code = -1 if code_raw is None else int(code_raw)`，与飞书适配器、本文件 `_handle_callback` 保持一致。

**`QQOfficialAdapter._verify_signature` — msg 拼接的冗余解码** Nit

```python
msg = (timestamp + raw_body.decode("utf-8", errors="replace")).encode("utf-8")
```

`raw_body` 已是 bytes。对有效 UTF-8 的 JSON（QQ 服务器发的总是）来说，`decode(errors="replace")` 再 `encode("utf-8")` 是恒等往返。对含非法 UTF-8 字节的请求体，往返后字节序列会变，验签必然失败（即使签名本来是对的）—— 这是潜在的正确性隐患。建议简化为 `msg = timestamp.encode("utf-8") + raw_body`，更直接也更省一次编解码。

**`QQOfficialAdapter.send()` — body 过滤** Nit

```python
body = {k: v for k, v in body.items() if v is not None and v != ""}
```

过滤 `""` 与当前场景自洽（主动推送不传 `msg_id`），但若未来 QQ API 要求 `event_id` 字段即使空也必须存在（如某些被动回复链路），会被这里静默丢弃。当前注释已说明"event_id 当前未支持"，可接受；后续若接入 event_id 场景需要回顾此过滤逻辑。

## 4. Security（安全）

**`FeishuAdapter` — 整体安全设计良好** ✅
- 明文模式未配置 `verification_token` 时 `raise ValueError` → 外层吞掉 → 返回 `{}` 不回 challenge（fail-closed，注释明确说明防止 fail-open 注入）
- 加密模式由 `encrypt_key` 证明身份，解密失败直接丢弃
- 所有事件处理异常被吞，始终返回 `200 {}`，防止飞书重试机制放大攻击
- 密钥（`app_secret`、`encrypt_key`）不出现在日志中；`app_id` 是公开标识符可接受

**`FeishuAdapter` — 加密模式与明文模式的混合攻击面** Consider

```python
# _handle_event() line 150-156
if event_type == "url_verification" or "challenge" in payload:
    if not self._encrypt_key:
        self._verify_token(payload)
    return {"challenge": payload.get("challenge", "")}
...
if not self._encrypt_key:
    self._verify_token(payload)
```

当 `encrypt_key` 已配置时，明文事件（`body` 中无 `encrypt` 字段，直接 dict）会跳过 `_verify_token`。这隐含一个假设："加密模式下的请求只能来自飞书基础设施"。

但如果攻击者能直接向 webhook 端口发明文请求（绕过飞书，例如 webhook 端口对公网开放、或反向代理配置不当），加密模式下的 webhook 将无认证接受该事件。攻击者可借此触发 `on_message` 注入伪造消息，或在 URL 校验阶段让飞书误以为校验通过。

**建议：** 当 `_encrypt_key` 已配置但 `_decode_payload` 返回的 body 不含 `encrypt` 字段（即非加密请求）时，直接拒绝或仍执行 token 校验，做到双重保险。这是低概率高代价的加固，生产部署值得加。

**`QQOfficialAdapter` — Ed25519 验签** ✅
- 所有 op=0 事件必经 `_verify_signature`，`X-Signature-Ed25519` + `X-Signature-Timestamp` + raw body 三段拼接验签
- 未配置 `secret` 时拒绝所有事件（fail-closed，"未配置 secret 时拒绝事件 (验签无法进行)"）
- 验签失败返回 `{"opcode": 12}` 而非 HTTP 401，不向调用方暴露签名细节

**`QQOfficialAdapter._derive_seed` — 短 secret 派生** Consider

```python
# isac/channel/adapters/qq_official/adapter.py:387-396
def _derive_seed(secret: str) -> bytes:
    s = secret or ""
    while len(s) < _ED25519_SEED_SIZE:
        s = s + s  # 双倍
    return s[:_ED25519_SEED_SIZE].encode("utf-8")
```

当 `secret` 长度 < 32 时，用"双倍直到 >=32"的方式派生 Ed25519 seed。如果 `secret="abc"`（3 字节），派生出的 seed 是 `abcabcabc...abc`（前 32 字节），即一个周期为 3 的低熵串。这与 QQ 官方文档"seed = bot_secret 重复双倍直到 >=32"的字面行为一致（注释也说明了 `strings.Repeat(s, 2)` 等价），但若 secret 本身短，seed 熵不会超过 secret 本身的熵。

**建议：** 文档级或运行时启动检查时提示用户：`bot_secret` 长度应 >= 32（官方通常给的就是 32+ 字符的 secret），否则在适配器启动时 warning 一次。这不是 bug，是配置卫生提示。

**日志安全** ✅
飞书 `start()` 中 `app_id=self._app_id` 落 info 日志。`app_id` 是公开标识符（出现在飞书应用页面 URL 中），可接受。QQ 适配器同理。`app_secret` / `secret` / `encrypt_key` 均未落日志。

## 5. Performance（性能）

**每次 HTTP 请求创建新的 `httpx.AsyncClient`** Consider

```python
# 两个适配器的 _http_post 都这样写:
async with httpx.AsyncClient(transport=transport) as client:
    resp = await client.post(...)
```

每次请求都新建 + 关闭一次 `AsyncClient`，TCP 连接无法复用，握手开销重复支付。低流量场景（私聊机器人、单群）完全可接受；若预期高频消息收发（活跃群聊机器人），建议在适配器实例中维护一个复用的 `AsyncClient`：`start()` 时构造、`stop()` 时 `aclose()`，`set_http_transport()` 改为替换 client 的 transport。这能把高频请求的握手成本降到一次性。

**token 缓存策略正确** ✅
两个适配器都用 `time.monotonic()` + 提前 60s 刷新窗口，避免了：
- 每次发消息都换取 token（会撞飞书/QQ 的 token 接口频控）
- 系统时钟回拨导致 token 失效判断错误
- token 临界过期（如 `expire=7200`，刚好用满 7200s 后下一秒就过期）

**scaffolding 测试实际绑定端口** Nit / Test Hygiene

`test_o4_platform_adapters_scaffolding.py` 的 `test_start_stop_noop` 用默认配置 `FeishuAdapter({})` / `QQOfficialAdapter({})` 启动适配器，会在测试运行期间**真实地**绑定 9099（飞书，127.0.0.1）与 8443（QQ，0.0.0.0）端口。uvicorn 的 `serve()` 在 `startup()` 阶段 bind socket，随后才检查 `should_exit`，所以即便 stop() 紧接着调用，端口也会被短暂占用。

**潜在问题：**
- 并行测试执行（pytest-xdist）下可能撞端口冲突
- 8443 是 0.0.0.0 监听，开发机上若有其他服务用同端口会偶发失败
- 端口 9099 / 8443 在 CI 环境（容器化）可能受限

**建议：** 测试构造适配器时显式传 `webhook_port=0`（让 OS 分配空闲端口）或用一个独立的测试端口范围（如 19099 / 18443），并把 `webhook_host` 改为 `127.0.0.1`（QQ 适配器默认 `0.0.0.0` 对测试不合适）。

**测试命名误导** Nit

`test_o4_platform_adapters_scaffolding.py` 与 `TestFeishuAdapterSkeleton` / `TestQQOfficialAdapterSkeleton` 类名里都带 "Skeleton"，但飞书与 QQ 官方适配器都是**真实实现**（非骨架），只有 `WeChatAdapter` 是真正的骨架。测试名容易让读者误以为这些适配器尚未实现，建议改为 `TestFeishuAdapterContract` / `TestQQOfficialAdapterContract` 之类反映实际语义的名字。
