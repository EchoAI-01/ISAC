## 二、新发现的 Critical 问题（5 项，均已复核确认）

### C-N1：`/api/v1/events/stream` 全量事件明文广播，scope 过滤对未知事件类型 fail-open

- **位置**：`isac/control/api/routes_events.py:122-130`（`_event_visible`）+ `isac/main.py:156,1148`
- **问题**：`_event_visible()` 对不在硬编码 4 项白名单（`_EVENT_TYPE_SCOPES`）内的事件类型直接放行（fail-open）。生产环境唯二真实触发的事件——`POST_MESSAGE`（payload 是完整 `ISACMessage`，含用户聊天原文）和 `ON_START`（payload 是**未脱敏的全局 config**，含 `control.api_token`/LLM `api_key`/webhook secret 等全部密钥）——都不带 `event_type` 字段，被归为 `"unknown"`，命中 fail-open 分支。
- **影响**：任何持有合法控制面凭证的调用方，即便 token 仅有 `usage:read` scope，都能通过 SSE 实时拿到全平台所有用户聊天原文和启动时的全部密钥。测试套件全部用手工构造的 `{"event_type": "agent.status_changed"}` 模拟，从未验证真实 payload 形态。
- **复核证据**：直接读取 `_event_visible`/`append`/`_subscribe_all_events` 源码及 `main.py` 两处 `fire_async` 调用点，确认两类敏感 payload 的形状与 fail-open 逻辑完全吻合。
- **修复方向**：未识别事件类型改默认拒绝；`ON_START` 不应携带原始 config；EventBus 内部对象进入 SSE 广播前必须经显式白名单/脱敏转换。

### C-N2：飞书 webhook 配置 `encrypt_key` 后，明文请求完全绕过验证

- **位置**：`isac/channel/adapters/feishu/adapter.py:143-181`（`_handle_event` / `_decode_payload`）
- **问题**：`_decode_payload` 只要请求体不含 `"encrypt"` 键就原样返回，不检查 `encrypt_key` 是否已配置；`_handle_event` 用 `if not self._encrypt_key: self._verify_token(...)` 决定是否验 token，隐含假设"配了 encrypt_key 就说明请求已经过加密验证"——这个假设对攻击者自己构造的明文请求不成立。
- **影响**：攻击者不需要知道 `encrypt_key` 也不需要知道 `verification_token`，直接 POST 明文 `im.message.receive_v1` JSON 即可让伪造消息进入 `on_message` 主链路。配置了"更安全"的加密模式反而完全禁用验证。
- **复核证据**：直接读取 `_decode_payload`/`_handle_event` 源码确认。
- **修复方向**：`self._encrypt_key` 非空时，请求体不含 `"encrypt"` 字段应直接拒绝。

### C-N3：QQ官方 webhook op=13 验证握手是签名 oracle，可伪造任意事件签名

- **位置**：`isac/channel/adapters/qq_official/adapter.py:168-180`（`_handle_validation`）vs `:182-221`（`_verify_signature`）
- **问题**：`_handle_validation`（op=13）对攻击者提供的任意 `plain_token`/`event_ts` 返回 `Ed25519_sign(event_ts + plain_token)`；`_verify_signature`（op=0 事件验签）验证的恰好是同一格式 `Ed25519_sign(timestamp + raw_body)`。
- **影响**：攻击者选一段伪造事件 JSON 作为 `plain_token` 请求签名，再把同一 JSON 原样作为 body 以 op=0 重新提交——验签通过，完全绕过（包括 R2 刚加的 timestamp 新鲜度校验）。
- **复核证据**：直接读取两个方法源码，逻辑推演确认签名格式完全重合。此机制可能部分源自官方协议设计，但 ISAC 侧未做域分隔/限流防护。
- **修复方向**：op=13 签名消息加域分隔前缀（如 `"VERIFY:" + event_ts + plain_token`），或限制该端点调用频率。

### C-N4：R16 打断注入防护标签未转义，可被用户消息字面文本提前闭合

- **位置**：`isac/agent/injectors/interrupt.py:64-76,111`（`_sanitize_reason`）
- **问题**：`_sanitize_reason` 只过滤不可打印字符和已知注入前缀，未对 `<`/`>`/`/` 做转义。用户消息若含字面 `</user_excerpt>`，拼接后会提前闭合标签，使后半段文本以"标签外文本"身份出现在 system prompt 里。
- **影响**：任意用户在 Agent 思考期发第二条消息即可触发，无需特殊权限。实际可利用程度取决于下游模型对标签语义的遵从度，但代码层防护缺口确定存在。
- **复核证据**：直接读取源码确认过滤逻辑不含 `<`/`>` 转义。
- **修复方向**：拼接前对 `reason` 做 `<`/`>` 转义。

### C-N5：VectorStore/GraphStore `close()` 未加锁，与 `upsert()`/`search()` 竞态，C1 修复不完整

- **位置**：`isac/memory/storage/vector.py:66-70`（`close`）vs `:89-96`（`upsert`，持锁）；GraphStore 同构
- **问题**：C1 给 `upsert`/`delete`/`init_schema` 加了 `_init_lock`，但 `close()` 未获取同一把锁，`search()`（读路径）完全不接入锁保护。
- **触发路径**：① `AgentManager.destroy(keep_memory=False)` 不等待该 Agent 在途记忆写入任务结束即清理；② 优雅关闭时 `drain_inflight()` 30s 超时后不取消残留任务就继续关闭链路。
- **影响**：`close()` 与并发中的 `upsert()` 交错，触发 `Cannot operate on a closed database` 被 `except Exception` 静默吞掉，导致记忆写入静默丢失。
- **复核证据**：直接读取 `vector.py` 源码确认 `close()` 无锁保护，与文档注释所述的锁保护范围不一致；两个独立子 Agent（memory 组、runtime 组）从不同触发路径独立收敛到同一根因。
- **架构建议（两组独立得出同一结论）**：`isac/runtime/manager.py:190` 的 `_purge_vector_and_graph`（同时是 ruff C901 复杂度告警来源）在 runtime 层用 `getattr`/`os.remove` 手工拼文件名清理，应下沉为 VectorStore/GraphStore 自身的 `purge_namespace()` 方法，由存储层在锁内完成"关闭+删文件"。R7 当前在 1442 个单测中零覆盖（`keep_memory=False` 从未被测试传入）。
