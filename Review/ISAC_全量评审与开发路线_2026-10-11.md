## 四、P0 待修缺陷精确定位 (2026-10-10 审计批次, 本轮逐项代码级复核确认)

### D1 [Major] 入站去重键缺会话维度

- **位置**: `isac/gateway/inbound_dedup.py:49` — `key = f"{platform}:{msg_id}"`
- **根因**: 去重键只有 `(platform, msg_id)` 两维。Telegram 的 `message_id` 是 **per-chat 独立递增序列**,Discord 同理;不同会话/群的消息 ID 必然撞号。A 会话先到的 `(telegram, 12345)` 会把 B 会话稍后到的同 ID 消息误判为重复而丢弃 —— **跨会话误吞真实消息**。
- **修复建议**: 键升为 `(platform, chat_id/session_id, msg_id)` 三维;调用方 (dispatch 入口) 传入会话键;补跨会话同 msg_id 回归测试。

### D2 [Major] tools_policy 非法档位 fail-open (安全)

- **位置**: `isac/agent/tools/registry.py:182-184` (`effective_policy` 配置层覆盖) × `registry.py:254/276/284` (execute waterfall)
- **根因链**: `ToolPermission.check()` (base.py:129-131) 对策略表内非法档位 fail-closed 归 deny ✅;但 `effective_policy()` 中配置层 (EnableMatrix 三层: 全局运维 → Agent → Channel) 返回的 `platform_policy` **非空即覆盖、无档位校验**。配置里笔误写 `"alow"` 等非法值 → 透传到 execute 管线 → `if policy == "ask"/"deny"/"restricted"` 均不匹配 → 落入阶段 3+4 **直接执行** = fail-open。且 `definitions()` (registry.py:203) 只过滤 `!= "deny"`,非法档位工具仍出现在 LLM schema。
- **修复建议**: `effective_policy` 对配置层返回值过 `_VALID_LEVELS` 校验,非法归 deny (与 check() 同口径);顺手在 `validate_config` 层对 tools_policy 值域做配置期校验 (fail-fast 在写入时)。

### D3 [Major] 压缩 GC 删除范围与摘要输入范围不一致 (数据丢失)

- **位置**: `isac/session/compressor.py:185-186` (输入截断) × `compressor.py:106/117` (GC 全量删)
- **根因**: `_build_original_text()` 把前缀文本截断到 `input_max_chars` (默认 6000) —— **截断点之后的事件内容未进摘要素材**;但 `source_seqs = [e.seq for e in prefix]` 取**全部**前缀,`delete_events()` 物理删除**全部**。结果:截断点之后的事件内容**既不在摘要里、又被物理删除**,从历史窗口永久丢失 (事件溯源的"无损"承诺被压缩链路打破)。
- **修复建议**: 按实际进入摘要的事件集合计算 `source_seqs`;或输入超限时拆批压缩 (本轮只压前 N 个事件,剩余留待下轮);补"超长会话压缩后截断点内容仍可召回"回归测试。

### D4 [Medium] 压缩摘要排序错位 (历史窗口语义)

- **位置**: `isac/session/history.py:98` (`_event_to_message` 的 `EVENT_TURN_COMPRESSED` 分支)
- **根因**: `turn.compressed` 事件 append 于分区末尾 (seq 最大),fold 按 seq 排序 → 压缩摘要出现在历史窗口**末尾 (最新位置)**,而它替代的是**最旧**的前缀对话。LLM 看到的顺序:活跃窗口消息之后突然出现一段"此前摘要",时序错乱。且摘要被标为 `role: "assistant"`,与"对话历史"语义混淆 (它是对历史的元描述,不是 bot 说过的话)。
- **修复建议**: fold 时把 turn.compressed 的消息**插入到它替代区间的起始位置** (source_seqs 最小值处),角色可用 system/前置 user 上下文语义;或多条压缩摘要按被替代区间排序。

### D5 [Major] 插件 reload 绕过 plugins_allow/deny (权限提升)

- **位置**: `isac/plugin/runtime/activation.py:141-149` (`_sync_one_instance`) × `activation.py:125-127` (全量模式)
- **根因**: 初始装配 `assembly.py:344` (`_merge_shared_plugin_tools`, H2) 按 `config.plugins_allow/plugins_deny` 过滤 ✅;但 reload/install 后的 `sync_plugin_tools_to_agents()` 把共享表中 `source=插件名` 的工具**直接 register 进每个 running Agent 的 registry,完全不查该 Agent 的启用矩阵**。Agent 配置 `plugins_deny: ["x"]` 或受限默认 `plugins_allow: []`,初始正确排除;运营方 `POST /plugins/x/reload` (或任一插件 reload 触发的全量 sync) 后工具被灌回 —— **绕过启用矩阵**。插件自带工具名不在 DEFAULT_POLICY 里 → 未声明默认 allow → 实际放行。
- **修复建议**: `_sync_one_instance` 取到 `instance.config` 后按 `_plugin_enabled_for` (assembly.py:316 同款判定) 过滤再 register;全量模式同样;补"deny 插件 reload 后仍不可见"回归测试。

> 五项共同特征:均为 2026-08-19 加固轮**之后**的新增代码或新接线引入 (去重/压缩是阶段 3-2 新模块,sync 是 C2 重构后路径),说明加固轮清的是存量,增量仍需一轮收口 —— 建议本批修复合并为一轮"增量收口轮",每项配对抗性回归测试。
